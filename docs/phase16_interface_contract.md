# Phase 16A: Interface Discovery & Demo Contract

## Overview

This document defines the formal, verified interface contract between the Phase 16 Real-Time Demonstration & Observability Console and the existing AI-Based Server-Client Load Balancer system. It is constructed from direct, read-only inspection of the repository source code, ensuring that the demonstration layer integrates seamlessly without modifying routing semantics or bypassing the central load balancer.

---

## Architectural Dependency Flow

The demonstration console acts as an external orchestration and monitoring layer. Traffic generated by the console flows strictly through the load balancer, exactly like external client traffic.

```
┌────────────────────────────────────────────────────────┐
│ Browser (Web Dashboard)                                │
│   - HTML5 / CSS3 / ES6 Vanilla JS                      │
│   - Real-time telemetry display & interactive controls │
└───────────────────────────┬────────────────────────────┘
                            │ HTTP / JSON API (:8080)
                            ▼
┌────────────────────────────────────────────────────────┐
│ Demo Control Layer (`demo/server.py` :8080)            │
│   - Serves dashboard UI assets                         │
│   - Exposes REST endpoints for configuration & control │
│   - Dispatches traffic via WorkloadGenerator to LB     │
│   - Polls /lb-metrics, /lb-health, and node /health   │
└─────────────┬───────────────────────────┬──────────────┘
              │                           │
              │ HTTP :8000                │ HTTP :8001 - :8003
              │ (Workloads & Health)      │ (Node Liveness & Telemetry)
              ▼                           ▼
┌────────────────────────────────────────────────────────┐
│ Existing Central Load Balancer (:8000)                 │
│   - Handles incoming requests at /process & /health    │
│   - Implements /lb-health and /lb-metrics endpoints    │
│   - Supports runtime algorithm update via /lb-algorithm│
└───────────────────────────┬────────────────────────────┘
                            │
                            │ Internal Dispatch
                            ▼
┌────────────────────────────────────────────────────────┐
│ Existing Routers (`load_balancer/router.py`)           │
│   - Round Robin, Least Connections, IP Hash            │
│   - MLRouter (LR, RF, DT, SVM, XGBoost)                │
│   - AdaptiveRouter (Policy & Learned Meta-Selector)    │
│   - PriorityDeadlineRouter                             │
└───────────────────────────┬────────────────────────────┘
                            │
                            │ Forwarded HTTP Requests
                            ▼
┌────────────────────────────────────────────────────────┐
│ Existing Backend Servers (1, 2, 3)                     │
│   - Ports: 8001, 8002, 8003                            │
│   - Endpoints: /health, /metrics, /process             │
└────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Zero-Bypass Guarantee**: The dashboard never routes requests directly to backend servers to simulate load balancing. All request routing is evaluated and executed by the central load balancer.

## 1. Load Balancer Startup Interface

- **Module**: `load_balancer/app.py`
- **Programmatic Factory**:
  ```python
  create_load_balancer(
      host: Optional[str] = None,         # Defaults to os.getenv("LB_HOST", "127.0.0.1")
      port: Optional[int] = None,         # Defaults to int(os.getenv("LB_PORT", "8000"))
      algorithm: Optional[str] = None,    # Defaults to os.getenv("ROUTING_ALGORITHM", "round_robin")
      backends: Optional[List[str]] = None,# Defaults to get_configured_backends()
      backend_timeout: Optional[float] = None, # Defaults to float(os.getenv("BACKEND_TIMEOUT", "2.0"))
      model_path: Optional[str] = None,   # Defaults to os.getenv("MODEL_PATH", None)
      adaptive_strategy: Optional[str] = None, # Defaults to os.getenv("ADAPTIVE_STRATEGY", "policy")
  ) -> ThreadingHTTPServer
  ```
- **Execution Entrypoint**:
  ```bash
  python -m load_balancer.app --host 127.0.0.1 --port 8000 --algorithm round_robin
  ```
- **CLI Options**:
  - `--host`: Host IP (default: `127.0.0.1` / `LB_HOST`)
  - `--port`: Listen port (default: `8000` / `LB_PORT`)
  - `--algorithm`: Algorithm choice (`round_robin`, `least_connections`, `ip_hash`, `ml`, `adaptive`, etc.)
  - `--adaptive-strategy`: Strategy choice (`policy`, `meta`)
  - `--backends`: Comma-separated backend URLs
  - `--model-path`: File path to serialized `.joblib` artifact
  - `--timeout`: Timeout in seconds (default: `2.0`)

## 2. Backend Startup Interface

- **Module**: `server/app.py`
- **Programmatic Factory**:
  ```python
  create_server(
      server_id: Optional[str] = None,    # Defaults to os.getenv("SERVER_ID", "server-1")
      host: Optional[str] = None,         # Defaults to os.getenv("SERVER_HOST", "127.0.0.1")
      port: Optional[int] = None,         # Defaults to int(os.getenv("SERVER_PORT", "8001"))
      max_workers: int = 20,              # Worker thread semaphore limit
  ) -> ThreadingHTTPServer
  ```
- **Execution Entrypoint**:
  ```bash
  python -m server.app --id server-1 --host 127.0.0.1 --port 8001 --workers 20
  ```
- **CLI Options**:
  - `--id`: Unique server ID (default: `server-1` / `SERVER_ID`)
  - `--host`: Host IP (default: `127.0.0.1` / `SERVER_HOST`)
  - `--port`: Port (default: `8001` / `SERVER_PORT`)
  - `--workers`: Concurrency limit (default: `20`)

## 7. Routing Algorithm Interface & Registry

- **Abstract Base**: `BaseRouter` in `load_balancer/router.py`:
  - `select(client_ip: Optional[str]) -> str`
  - `release(backend: str, success: bool)`
  - `route(client_ip: Optional[str]) -> ContextManager[str]`
  - `set_healthy_backends(healthy: Optional[List[str]])`
  - `get_candidate_backends() -> List[str]`

- **Supported & Verified Algorithms**:
  1. `round_robin`: `RoundRobinRouter` (sequential cyclic dispatch)
  2. `least_connections`: `LeastConnectionsRouter` (lowest active connections with lowest-index tie-breaking)
  3. `ip_hash`: `IPHashRouter` (MD5 client IP hash modulo active candidate count)
  4. `logistic_regression` / `ml`: `MLRouter` (`models/logistic_regression.joblib`)
  5. `random_forest`: `MLRouter` (`models/random_forest.joblib`)
  6. `decision_tree`: `MLRouter` (`models/decision_tree.joblib`)
  7. `svm`: `MLRouter` (`models/svm.joblib`)
  8. `xgboost`: `MLRouter` (`models/xgboost.joblib`)
  9. `adaptive_policy`: `AdaptiveRouter` (strategy: `"policy"`)
  10. `adaptive_meta`: `AdaptiveRouter` (strategy: `"meta"`, `models/meta_selector.joblib`)
  11. `priority_ml`: `PriorityDeadlineRouter` wrapping `MLRouter`
  12. `priority_adaptive`: `PriorityDeadlineRouter` wrapping `AdaptiveRouter`

## 9. Adaptive Routing Telemetry Interface

When `AdaptiveRouter` executes, it exposes decision metadata via attributes and response headers:
- `selected_model`: Name of model chosen for this request (`Random Forest`, `SVM`, etc.)
- `selector_confidence`: Confidence score of the adaptive selector
- `selection_reason`: Operating regime rule or meta-model confidence
- `model_selection_time_ms`: Time taken to choose the model
- `ml_predicted_server`: Target server predicted by chosen model
- `ml_confidence`: Prediction probability of the chosen model
- `is_fallback`: Boolean indicating whether safety fallback to Least Connections occurred
- `switch_count`: Total number of model transitions
- `switch_rate`: Transitions per total routed requests

## 14. Failure, Blackout & Timeout Semantics

- **Single Node Crash**: Detected via `URLError`; marked in unhealthy cache for 3.0s; request immediately fails over to surviving candidate.
- **Total Blackout (0 backends available)**: Load balancer returns clean HTTP `502 Bad Gateway` (or `503 Service Unavailable`). Process does **not** crash.
- **Backend Request Timeout**: Returns HTTP `504 Gateway Timeout` when backend execution exceeds `BACKEND_TIMEOUT` (default 2.0s).

## 16. Research Alignment & Outcome C Preservation

The demonstration console strictly adheres to the empirical findings established in Phase 14:
- **Outcome C (Heuristic Dominance)**: Conventional heuristics (Round Robin, Least Connections) achieve lower end-to-end latency due to zero polling and inference overhead. ML and Adaptive routing provide proactive imbalance prevention under high load and non-stationary stress.
- **Metric Integrity**: All performance numbers, latencies, and routing decisions displayed in the console represent real, live HTTP requests and server metrics. Zero metric fabrication or artificial advantages are encoded.
